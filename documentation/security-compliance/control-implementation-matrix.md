# DESC Control Implementation Matrix — Mizan

> **Mandatory across every layer.** Ref: `CLAUDE.md` §11. A control is **not done until
> its evidence entry exists.** Update this file whenever a control lands.
>
> Status legend: ☐ not started · ◐ in progress · ☑ implemented (dev) · ✔ verified (with evidence)
> Environment note: in development some controls are implemented but not production-grade
> (self-signed cert, unencrypted host volume, local backups) — see §11.2. The gap is recorded,
> the control is **never removed**.

|---|---------|:---:|------------------|
| 1 | Encryption in transit (TLS at nginx, HSTS, TLS 1.2 min) | ☑ | `infrastructure/nginx/nginx.production.conf`: TLS 1.2/1.3 only, modern ECDHE ciphers, no session tickets, HSTS with subdomains, HTTP → HTTPS. `scripts/check-production-host.sh` refuses a self-signed or expiring certificate. Development uses a self-signed certificate (§11.2). Verification on the target server pending (first install) |
| 2 | Encryption at rest (encrypted PG volume, MinIO SSE) | ☑ | `docker-compose.production.yml` keeps every volume under `MIZAN_DATA_DIRECTORY`; the host check requires it to be on a dm-crypt (LUKS) device and failed correctly on the unencrypted dev disk. Backups are AES-256 encrypted on top (control 17). MinIO is not used (OPEN-QUESTIONS #23). Development disk is unencrypted (§11.2). Verification on the target server pending |
| 3 | Password storage (argon2id, ≥12 chars, blocklist) | ✔ | `@node-rs/argon2` (argon2id). **Policy enforced** on user create/update — `user.schema.ts` requires ≥12 chars + a common-password blocklist. Verified (weak password → 400) |
| 4 | Session management (JWT 15m/refresh 7d, rotated, revocable) | ✔ | Server-side sessions (`AuthSession` table, migration `20261001084802_auth_sessions`, `auth-session.repository.ts`). Both tokens carry the session id; every request checks the session is open (cached ≤ `SESSION_CHECK_CACHE_SECONDS`, cleared at once on revoke). Refresh tokens rotate on each use; only a SHA-256 hash is stored; reuse of a spent refresh token ends the whole session and is audited (`SESSION_REFRESH_REUSE`). Sign-out, deactivation, password change and the admin "End sessions" action revoke sessions (`USER_SESSIONS_ENDED` audited). Frontend refresh is single-flight within a tab and serialised across tabs (Web Locks), so legitimate use never looks like reuse. Evidence: `authentication.sessions.spec.ts` (7 tests) and a live run on 2026-10-01: rotation, reuse refused and session ended, sign-out, admin end-sessions. Deviation: PostgreSQL instead of the Redis denylist, see OPEN-QUESTIONS #20 |
| 5 | Account lockout (5 attempts → 15m lock, audited) | ☑ | Enforced in `authentication.service.ts` (`ACCOUNT_LOCKOUT_ATTEMPTS`/`_MINUTES`); `ACCOUNT_LOCKED` audit row written |
| 6 | Idle timeout (30m → re-auth) | ✔ | `SESSION_IDLE_TIMEOUT_MINUTES` (30) served by `GET /system/info`; enforced in the app shell by `idle-timeout.hook.ts`: activity (pointer, key, wheel, touch, scanner keystrokes) is shared across tabs, a warning with a countdown appears in the last minute (`IdleTimeoutWarning.tsx`), then `POST /auth/logout` (audited) clears the session and the login page says why. Sign-in starts the clock. Evidence: browser run on 2026-10-01 with a fast-forwarded clock: warning at 29m10s, cleared by "Stay signed in", signed out after 31 idle minutes. Limitation: enforcement is in the client; a stolen refresh token is control 4's concern (server-side revocation still pending) |
| 7 | Multi-factor (TOTP built, `MFA_ENABLED=false`) | ✔ | Built and verified; **off by default** (`MFA_ENABLED=false`) as the spec requires, so certification switches it on by configuration. `multi-factor.service.ts`: RFC 6238 TOTP (otplib), ±1 step for clock drift, each step accepted once (`mfaLastUsedStep`), secret stored AES-256-GCM encrypted with `MFA_ENCRYPTION_KEY`, QR drawn on the server (no external call). Sign-in returns a 5-minute challenge, never a session, until the code is right; wrong codes count towards account lockout (control 5). First sign-in after it is switched on walks the person through enrolment. Admin "Reset two-step" for a lost phone clears it and ends that user's sessions. Machine accounts may be exempted only via `MFA_EXEMPT_ACCOUNTS` and only from `MFA_EXEMPT_NETWORKS` (default: this server). Audit: `LOGIN_MFA_CHALLENGE`, `MFA_FAILED`, `MFA_ENROLLED`, `USER_MFA_RESET`, `LOGIN_SUCCESS` with `secondFactor`. Evidence: `multi-factor.spec.ts` (8 tests); browser run on 2026-10-01 against a backend with MFA on (enrolment by QR key, wrong code refused, code sign-in, second sign-in, Arabic dark), then admin reset. Before switching on: set `MFA_ENCRYPTION_KEY`, give the AI service its own account (OPEN-QUESTIONS #21) |
| 8 | Access control (role guards at controller, never client-trusted) | ☑ | `JwtAuthGuard` + `RolesGuard` + `@Roles()`; verified store keeper → 403 on `/users` |
| 9 | Audit logging (every state change writes `AuditLog` in same tx) | ☑ | Auth events audited; stock movements write `STOCK_*` `AuditLog` (with before/after) **inside the same `$transaction`** (`stock-movements.service.ts`). Pattern to reuse for all future state changes. Extended to the assistant: every `POST /assistant/query` writes an `ASSISTANT_QUERY` audit row (`assistant.service.ts`) — not a state change, but every question a user asks the AI is logged like any other action |
| 10 | Log immutability (PG rule blocks UPDATE/DELETE) | ☑ | **Applied to live DB** — 4 rules on `AuditLog`/`StockMovement`, verified via `pg_rules`. `database/migrations/0001_append_only_rules.sql` |
| 11 | Network segmentation (AI + DB unreachable from outside Docker net) | ☑ | `docker-compose.production.yml`: only nginx publishes ports (`public`); `edge` and `data` are `internal: true` Docker networks; the AI service, Ollama and PostgreSQL sit only on `data`, so they have **no route to the internet** and cannot be reached from outside; only the backend joins `mail` for SMTP. On the dev board today the AI service binds 127.0.0.1 only (equivalent isolation, native run). Verification on the target server pending |
| 12 | Rate limiting on `/auth/*` | ✔ | `@nestjs/throttler` via `security/rate-limiting/` — `AuthRateLimitGuard` on the whole `AuthenticationController`, per client IP and per endpoint, `AUTH_RATE_LIMIT_MAX_REQUESTS` (10) per `AUTH_RATE_LIMIT_WINDOW_SECONDS` (60). Refusal is HTTP 429 with the bilingual `RATE_LIMITED` error. Evidence: `auth-rate-limit.guard.spec.ts` (3 tests) and a live run on 2026-10-01 (10 × 401, then 429). `TRUST_PROXY` makes `req.ip` the real client behind nginx. Dev caveat: through the Vite proxy every browser shares 127.0.0.1, so the limit is effectively per machine in dev. In-memory counters suit the single API instance; swap to Redis storage only if the API is scaled out |
| 13 | Secure headers (Helmet, strict CSP, no inline scripts) | ✔ | **API** (`backend/src/main.ts`): Helmet with `default-src 'none'; frame-ancestors 'none'` on every response, since it only returns data; the API docs page has its own narrower policy and is off in production (`SWAGGER_ENABLED`). **Web app**: one policy, `infrastructure/nginx/security-headers.conf` (`script-src 'self'`, `style-src 'self'`, no inline code, no eval, no external hosts, `frame-ancestors 'none'`, plus nosniff, no-referrer, DENY framing, Permissions-Policy); `vite preview` serves the built app with the same line. Label printing was rebuilt without a popup's inline script/style; fonts are never inlined. Evidence: browser run on 2026-10-01 over the built app, all 16 screens plus label printing and the assistant: 0 violations |
| 14 | Secrets management (env only, `.env*` git-ignored) | ☑ | `.env.example` committed; real `.env*` git-ignored (`.gitignore` pending) |
| 15 | Log hygiene (no PII; user IDs only) | ✔ | Pino JSON logs via `nestjs-pino` (`security/log-hygiene/`). Request logs keep only id, method, path (query string dropped), status, response time and `userId`. `redact` scrubs passwords, password hashes, MFA secrets, tokens, emails, IP addresses and auth/cookie headers at any depth; a log hook masks email-shaped text inside messages (e.g. SMTP errors quoting a recipient). Email service no longer logs recipient addresses. Evidence: `log-redaction.spec.ts` (4 tests) and a live capture on 2026-10-01: an authenticated request logged with `userId` only, no token, no search text. The audit log (control 9) remains the place that records actor and IP |
| 16 | Dependency scanning (`pnpm audit`, `pip-audit` in pipeline) | ☑ | `scripts/run-dependency-scan.sh`: `npm audit` (the project uses npm, not pnpm) for frontend and backend, full and runtime-only, plus `pip-audit` on `ai-service/requirements.txt`. Writes dated JSON and `summary.md` to `dependency-scan-reports/<date>/`, exits non-zero on runtime high/critical or any Python advisory, ready to gate a build. First run 2026-10-01: non-breaking fixes applied; open findings and their order in `dependency-scan-reports/2026-10-01/remediation.md`. Not yet in a CI pipeline, because none exists; run it before each release |
| 17 | Backup & recovery (automated encrypted backups, tested restore) | ☑ | `scripts/backup-database.sh` (pg_dump → AES-256 with a key file, checksum, retention), `restore-database.sh` (checksum first, refuses to overwrite live without confirmation), `verify-backup-restore.sh` (restore into a throwaway database, compare all row counts, confirm append-only rules, dated record). Procedure, key handling and schedule: `backup-and-recovery-procedure.md`. Tested restore: `restore-test-records/2026-10-01-restore-test.md` (PASS). Dev gap (§11.2): not yet scheduled, no off-site copy; both belong to the production server |
